## 7. 面试 3 分钟介绍

```text
这个项目是一个交易域离线数仓项目，目标是从单日学习样例升级成更接近真实业务的 7 天离线跑批项目。

首先在数据设计上，我覆盖了交易域常见场景，包括正常订单、未支付订单、取消订单、部分退款、全额退款、跨天支付、跨天退款、支付金额不一致、重复订单、空主键、负金额，以及退款金额大于订单金额这类业务异常。

然后在数仓分层上，我按 ODS/DWD/FCT/DWS/ADS 实现。DWD 层主要做清洗和 dirty 分流，例如订单 id 为空、用户 id 为空、金额为负、重复订单都会进入 dirty 表；clean 表只保留下游可信数据。FCT 层沉淀订单事实、订单状态事实和退款状态事实，统一取消订单、退款订单和净 GMV 口径。DWS 层做可复用汇总，ADS 层输出面向分析和报表的指标。

指标口径上，我区分 raw_order_cnt、valid_order_cnt、cancel_order_cnt、gross_valid_gmv、refund_amount、net_gmv。取消订单不进入有效 GMV，退款不直接改订单原金额，而是保留 amount、refund_amount 和 net_amount，这样既能看原始交易规模，也能看退款后的净 GMV。

数据质量上，我做了三类校验：第一类是单表校验，比如空主键、重复数据、负金额；第二类是跨层对账，比如 DWS 对 FCT，ADS 对 DWS；第三类是异常明细沉淀，比如超额退款和支付金额不一致。项目里有一笔订单金额 50、退款 80 的异常，DWD 不静默修正，FCT 暴露出负净额，DQ 记录异常，后续还能观察它传导到商品和渠道主题。

工程化上，我把手动 SQL 回刷封装成 Python runner，支持 start_dt/end_dt 范围补数、subject 参数按主题执行、SQL 模板渲染、日志记录、质量失败阻断和异常观察模式。最后接入 Airflow DAG，把 DWD、FCT、异常沉淀、DWS/ADS、支付对账、多主题分析拆成多个 task，可以在 UI 里看依赖、日志和失败重跑。
```

## 8. 高频面试问答

### Q1：你这个项目的数据分层是怎么设计的？

答：

```text
我按 ODS/DWD/FCT/DWS/ADS 分层。

ODS 或源数据层保存原始 demo 数据。
DWD 做字段规范化、脏数据识别和 clean/dirty 分流。
FCT 沉淀订单粒度事实，比如订单事实、订单状态事实、退款状态事实。
DWS 做可复用汇总，比如用户日汇总、用户等级交易汇总、商品品类汇总、渠道汇总。
ADS 面向最终分析指标，比如订单概览、退款概览、支付对账概览、多主题统一 ADS。
```

### Q2：DWD clean 表和 dirty 表怎么分？

答：

```text
clean 表只保留下游可信数据，dirty 表保留结构不合法或重复的数据，并记录 dirty_reason。

比如 order_id 为空、user_id 为空、order_date 为空、amount 为空、amount 小于 0 都进入 dirty。
重复 order_id 会用 row_number 去重，保留排序规则下的一条，其余进入 dirty，dirty_reason 是 duplicate_order_id。

这样做的好处是下游 FCT 不用反复处理基础脏数据，同时异常数据没有丢，可以回溯。
```

### Q3：取消订单和退款订单的口径有什么区别？

答：

```text
取消订单表示交易没有成为有效订单，所以不进入有效 GMV，net_amount 记为 0。

退款订单表示订单曾经是有效交易，但后续发生售后退款，所以我不会直接改订单原金额，而是保留 amount、refund_amount 和 net_amount。

也就是：
取消订单：net_amount = 0
有效未退款订单：net_amount = amount
有效已退款订单：net_amount = amount - refund_amount
```

### Q4：为什么退款不是直接改订单金额？

答：

```text
因为订单金额代表原始交易规模，退款金额代表售后冲减，两者分析价值不同。

如果直接把订单金额改小，就看不到原始 GMV，也不好分析退款率。
所以我保留 amount、refund_amount、net_amount，既能看交易规模，也能看退款后的真实净 GMV。
```

### Q5：跨天退款怎么处理？

答：

```text
项目里有一笔 2026-03-04 的订单，在 2026-03-06 发生退款。

我当前采用的是订单归因口径，也就是退款影响回填到原订单分区。
这样 2026-03-04 的订单净额会被这笔跨天退款影响。

如果业务要看资金流或退款事件趋势，也可以另做一套按 refund_dt 归因的退款事件 ADS。
```

### Q6：DWS 和 ADS 有什么区别？

答：

```text
DWS 是可复用中间汇总层，不直接面向最终报表。
ADS 是面向应用、报表或分析的最终指标层。

比如 fct_order_refund_status_di 可以先汇总到 dws_user_order_refund_day_agg，再由 ADS 输出全站退款概览。
这样后续如果有多个 ADS 需要用户日粒度指标，就可以复用 DWS，而不是每个 ADS 都扫事实表。
```

### Q7：你怎么做跨层对账？

答：

```text
我的原则是谁喂给下游，下游就先跟谁对账。

DWS 是由 FCT 喂数，所以 DWS 对 FCT。
ADS 是由 DWS 喂数，所以 ADS 对 DWS。
统一多主题 ADS 是由用户、商品、渠道三个主题 ADS 喂数，所以统一 ADS 对主题 ADS。

对账指标包括行数、订单数、金额、退款金额、净额等。
```

### Q8：你项目里的 DQ 体系有哪些？

答：

```text
我做了三类 DQ。

第一类是单表质量校验，比如主键不能为空、金额不能为负、同一粒度不能重复。
第二类是跨层指标对账，比如 DWS 对 FCT、ADS 对 DWS。
第三类是异常明细沉淀，比如退款金额大于订单金额、支付金额不一致、有订单无支付。

这样既能保证每一层表自身可信，也能保证指标在层间流转时没有丢失或放大。
```

### Q9：订单金额 50，退款 80，你怎么处理？

答：

```text
这个属于业务异常，不是简单的字段清洗问题。

我的处理是：DWD 保留这条结构合法的退款事件，因为它字段不为空、退款金额也大于 0；到 FCT 层计算出 refund_amount > amount 和 net_amount < 0；然后 DQ 把它记录到异常明细表，anomaly_type 是 refund_amount_over_order，anomaly_level 是 BLOCKER。

生产上这种 BLOCKER 日期应该阻断可信 ADS。学习项目里我保留了 allow-quality-fail，用来观察异常如何传导到商品和渠道主题。
```

### Q10：支付对账怎么做？

答：

```text
支付对账是用订单事实和支付事实按 order_id 做 full outer join。

对账状态分四类：
matched：订单金额等于支付金额
amount_mismatch：订单金额和支付金额不一致
order_without_payment：有订单，没有支付
payment_without_order：有支付，没有订单

差异金额是 diff_amount = order_amount - pay_amount。
diff_amount 大于 0 表示少付，小于 0 表示多付。
```

### Q11：支付对账和退款主题有什么区别？

答：

```text
退款主题关注售后后净 GMV，也就是订单金额被退款冲减后还剩多少。

支付对账关注财务一致性，也就是订单应付金额和实际支付金额是否一致。

它们都在交易域里，但解决的问题不同。退款影响净 GMV 口径，支付对账主要沉淀支付异常，不直接修改订单指标。
```

### Q12：商品主题为什么需要订单明细？

答：

```text
订单事实是一行一笔订单，只能回答订单级问题。
商品主题要按品类、商品看交易，所以必须引入订单明细粒度，也就是一行一个订单商品明细。

难点是订单级退款金额怎么分摊到商品明细。我这里用 item_amount / order_amount 的比例，把订单退款金额分摊到明细行，再汇总到品类。
```

### Q13：用户、商品、渠道多主题是不是重新算了一套交易指标？

答：

```text
不是。

多主题分析是把同一套交易事实接到不同维度上。
用户主题按用户等级看交易贡献，商品主题按品类看交易结构，渠道主题按来源看交易来源。

统一多主题 ADS 也不是重新从 FCT 算，而是汇总三个主题 ADS，避免口径分散。
```

### Q14：Python runner 做了什么？

答：

```text
Python runner 主要负责把手动跑 SQL 升级成工程化跑批。

它支持 start_dt/end_dt 范围补数，支持 subject 参数选择跑 DWD、FCT、支付、多主题等链路。
脚本会渲染 SQL 模板，生成 generated SQL，复制到 Spark 容器执行，记录日志，并在质量检查失败时阻断。

另外我加了 allow-quality-fail，用来在学习项目里观察预期异常传导。
```

### Q15：Airflow DAG 怎么设计的？

答：

```text
Airflow DAG 不是把所有东西塞到一个大 task，而是按主题拆成多个 task：

validate_params
-> run_dwd_order
-> run_fct_order
-> run_refund_anomaly
-> run_dws_ads
-> run_payment
-> run_multi_theme

这样 UI 里能看到任务依赖，某个环节失败也能定位到具体主题，并且可以 Clear 单个 task 重跑。
```

### Q16：如果让你把这个项目继续优化，你会做什么？

答：

```text
第一，我会把按订单归因的退款指标和按退款事件日期归因的指标拆开，支持不同业务分析口径。
第二，我会把 DQ 结果做成统一告警或报表，而不仅仅是落表。
第三，我会把 runner 的 subject 配置抽成 YAML，减少代码里的硬编码模板列表。
第四，如果进入实时方向，可以把订单和支付接入 Kafka/Flink，做实时支付对账或实时交易大盘。
```

## 9. 面试官可能追问的细节

### 追问：为什么 FCT 层要单独做订单状态事实和退款状态事实？

答：

```text
订单事实只表示一笔订单的基础信息。
订单状态事实补充取消状态，用来区分 raw_order 和 valid_order。
退款状态事实进一步补充退款金额和净额，用来计算退款率和净 GMV。

分开做的好处是学习和口径更清晰：取消影响有效交易口径，退款影响净 GMV 口径。
```

### 追问：你怎么防止 JOIN 粒度放大？

答：

```text
首先每张事实表和维表都会保证自己的粒度唯一。
比如订单事实是一行一笔订单，渠道事实是一行一个订单渠道，商品明细是一行一个订单商品。

其次 DQ 会检查重复粒度，比如 order_id 重复、user_level 重复、主题维度重复。
商品主题由于本身是明细粒度，所以会先在明细粒度上处理，再按品类汇总，避免直接把订单事实和多行明细乱 join 后造成金额放大。
```

### 追问：为什么 03-07 有异常还让 Airflow 继续跑？

答：

```text
这是学习项目里的异常观察模式。

真实生产里，BLOCKER 异常应该阻断可信 ADS。
但这个项目里我故意保留 03-07 的超额退款，让它继续传导到 DWS/ADS 和多主题 ADS，用来验证 DQ 是否能在下游识别负净额和退款率大于 1。

所以 runner 支持两种模式：默认严格阻断，allow-quality-fail 用于观察预期异常。
```

### 追问：你这个项目和真实公司项目还有什么差距？

答：

```text
主要差距有三点。

第一，数据规模是 demo 级，真实公司会涉及更大的数据量和性能优化。
第二，调度和告警还比较基础，真实项目会接入 SLA、告警、权限和发布流程。
第三，指标口径在真实公司需要和业务、产品、财务共同确认，我这里是按学习项目自己定义的交易域口径。

但项目已经覆盖了离线数仓最核心的工程链路：分层建模、指标口径、DQ 对账、异常沉淀、范围补数和 Airflow 调度。
```
